# ひとまず Vercel で公開し、65banseki.dev をつなぐ

- 日付: 2026-11-03
- 状態: 採用（暫定。ホスティング先は後で見直してよい）

## 決めたこと

| 項目           | 決めたこと                                                                                                        |
| -------------- | ----------------------------------------------------------------------------------------------------------------- |
| ホスティング   | Vercel の Hobby プランに置く。GitHub と連携し、`main` への push で本番に出す                                      |
| ブランチ       | 作業ブランチ → `dev`（プレビュー）→ `main`（本番）の順に取り込む。GitHub のデフォルトブランチは `dev`             |
| ドメイン       | Cloudflare で買った `65banseki.dev` を使う。`www.65banseki.dev` を正とし、`65banseki.dev` は 308 でそこへ転送する |
| DNS            | Cloudflare の DNS のままにし、Vercel を指すレコードを足す。Cloudflare のプロキシは使わない（DNS only）            |
| GitHub         | `hi-lee-mon/65-blog-app` を public で作る                                                                         |
| `metadataBase` | `app/layout.tsx` に `https://www.65banseki.dev` を書く                                                            |

設計書（`docs/design/20260925-blog-design-proposal.md`）で「今回は論じていない」としていたホスティング先とドメインを、ここで決める。

## 理由

### Vercel を選んだ理由

`next.config.ts` で `cacheComponents`・`partialPrefetching` と、`experimental` の機能を有効にしている。Vercel は Next.js の開発元で、こうした新しい機能がそのまま動く。いまは「とりあえず公開して、シェア用の画像を SNS で確かめたい」段階なので、動かすための手間が少ないことを優先した。

| 候補                                  | 採らなかった理由                                                                                  |
| ------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Cloudflare Workers（OpenNext で変換） | ドメインと同じ Cloudflare にまとめられる。ただ、上の新しい機能がどこまで動くかを確かめていない    |
| 静的書き出し（`output: "export"`）    | ルートハンドラーやキャッシュの仕組みの一部が使えなくなり、学習用に試している機能と相性が悪い      |
| Vercel CLI で手元から出す             | GitHub を使わずに済むが、CLI を `devDependencies` に足すことになる。push で出るほうが手順が少ない |

### `www` を正にする理由

本人の判断（2026-11-03）による。DNS のもともとの決まりでは、`www` の付かない形（ドメインそのもの）に CNAME を書けない。Cloudflare は CNAME flattening という独自の仕組みでこれを埋めているが、正の住所をその仕組みに頼らせると、DNS の管理元を移すときに困る。`metadataBase` を Vercel の環境変数に頼らせないのと同じ考え方で、標準の決まりだけで動く `www` を正にした。Vercel の既定もこの形。

`65banseki.dev` から `www` へ転送するために、`@` の CNAME（CNAME flattening）は引き続き使う。管理元を移すときは、この1行だけを移し先のやり方で書き直せばよい。

### プロキシを使わない理由

Vercel は「Cloudflare は DNS としてだけ使い、プロキシは切る」形を勧めている。プロキシを挟むと、Vercel のボット対策が効かなくなり、Cloudflare 側に古いページが残ることがある（[Using Cloudflare and other reverse proxies with Vercel](https://vercel.com/kb/guide/can-i-use-a-proxy-on-top-of-my-vercel-deployment)）。

### `metadataBase` を書く理由

Vercel の上では、`metadataBase` がなくても Next.js が環境変数 `VERCEL_PROJECT_PRODUCTION_URL` から本番の住所を補う（`node_modules/next/dist/lib/metadata/resolvers/resolve-url.js` で確認）。それでも書くのは、次の2つのため。

- 手元のビルドでは補う値がなく、`og:image` が `http://localhost:3000/...` になる。ビルドのたびに警告も出る
- 補う仕組みは Vercel の環境変数に頼っている。原稿の読み込み処理を Next.js に依存させない方針と同じく、置き場所を移しても住所が変わらないようにしておく

### public にする理由

本人の判断（2026-11-03）による。学習の過程をコードごと見せられるようにしておきたいため。

全コミットの作者欄には個人のメールアドレスが入っており、public にするとそのまま読める。本人はこれを承知のうえで public を選んだ。push の前に、履歴全体に秘密の値の形と、公開して困る語がないことを確かめた。

## 影響と残る課題

- Hobby プランは個人の非商用に限られる。広告や有料の記事を載せるなら見直す
- Vercel が使う bun の版は手元（1.4.4）と同じとは限らない。`bunfig.toml` の `minimumReleaseAge` とセキュリティスキャナーは bun 1.3 以降の機能なので、ビルドログで版を確かめる
- 作者欄のメールアドレスを隠したくなったら、以後のコミットを GitHub の noreply アドレスで作る。公開済みの履歴を書き換えても、すでに取得された写しからは消えない
- サイト全体の `title`・`description` は create-next-app の仮の値（「Create Next App」）のまま公開される
