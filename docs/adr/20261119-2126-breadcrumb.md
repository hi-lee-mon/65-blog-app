# パンくずリストを、各ページから中身を渡す Server Component で作る

- 日付: 2026-11-19
- 状態: 採用
- 関連: ADR `20261115-2117-publishable-home-before-storybook.md`（3-2 の位置づけ）、ADR `20261115-2130-site-header-footer.md`（ヘッダーとスキップリンク）、ADR `20260925-1702-two-layer-site-structure.md`（母屋と展示室）、ADR `20261119-0130-link-pending-indicator.md`（`AppLink`）

## 背景

記事は、検索や X のリンクから直接開かれることが多い。3-1 のヘッダーは「記事」「タグ」という区画までしか示さないので、直接来た人には、その記事がサイトの階層のどこにあるかが分からない。

WCAG 2.2 の 2.4.8「現在位置」（AAA）は、パンくずリストを満たし方の1つに挙げている。AAA なので、3-0 の自動検査では見ていない。

参考にした資料は次のとおり。

- WAI-ARIA APG「Breadcrumb Pattern」: `nav` に名前を付け、今のページへのリンクに `aria-current="page"` を付ける。実装例では、区切り記号を CSS で描いて読み上げから外している
- デジタル庁デザインシステム「パンくずリスト」（v2.18.3）: ヘッダーとページ見出しの間に置き、長いときは折り返す。React 版の実装では、今のページは `aria-current="page"` を付けた文字、区切りは `aria-hidden` の SVG、名前は「現在位置」
- Next.js 16.4 の同梱ドキュメント（`layout.md`）: レイアウトに置いた Client Component で、`usePathname` からパンくずを組み立てる例がある

## 決めたこと

- `app/_components/breadcrumb.tsx` に `Breadcrumb` を作る。上の階層の列（`parents`）と、今のページの名前（`current`）を別々に受け取る。今のページにリンクを付け間違える書き方を、型の段階でできなくするため
- `Breadcrumb` は Server Component にする。中身は各ページから渡す
- 置くのは記事一覧・記事・タグ一覧・タグ別の4種類のページ。ホームと展示室（`/design-system`）には置かない
- 置く場所は `main` の中、ページの見出しの前
- 記事ページでは `article` の外に幅を持つ `div` を作り、パンくずを `article` の外に出す
- `nav` に `aria-label="現在位置"` を付け、項目は `ol` と `li` で並べる
- 今のページはリンクにせず、`aria-current="page"` を付けた `span` にする
- 区切りの「/」は `aria-hidden="true"` の `span` に入れ、`li` の中に置く
- 長いときは折り返す（`flexWrap: "wrap"`）
- リンクには、この回では `next/link` をそのまま使う。3-1b の `AppLink` ができたら差し替える
- 検索エンジン向けの構造化データ（JSON-LD の `BreadcrumbList`）は、この回では作らない

## 採らなかった案

- **レイアウトに置き、`usePathname` で URL から組み立てる（Next.js 公式の例）。** 1か所に書けば全ページに出て、`main` の外にも置ける。しかし URL には slug しかなく、記事の題を出せない。部品が Client Component になる
- **レイアウトに並列ルート（Parallel Routes）の差し込み口を作る。** `main` の外に置けて記事の題も出せるが、ページごとに `@breadcrumb/...` のファイルが増え、今のサイトの大きさに対して仕組みが重い
- **今のページもリンクにする（APG の実装例の形）。** 押しても同じページが開くだけで、キーボードで使う人が Tab で止まる場所が増える
- **区切りを CSS の `content` で描く。** HTML に飾りの要素が増えないが、`content` の文字は読み上げられることがあり、読み上げから外していることがコードから見えにくい
- **履歴型のパンくず（たどってきた道を見せる）。** ブラウザの「戻る」と役割が重なり、人によって表示が変わる

## 確認事項の推奨と理由・欠点

確認事項は、チケットの「確認事項」と同じ内容。

1. **どこで組み立てるか。** 推奨は「各ページから渡す」。理由は、記事の題を知っているのがページだけで、Server Component のままにできるため。欠点は、ページを増やすたびに書き足す必要があり、書き忘れても検査では見つからないこと
2. **今のページをリンクにするか。** 推奨は「しない」。理由は、Tab で止まる場所を増やさないため。欠点は、APG の実装例とは違う形になること。また、フォーカスできない `span` に付けた `aria-current` は、読み上げソフトによっては読まれないおそれがある（VoiceOver では未確認）
3. **区切り記号の作り方。** 推奨は「`aria-hidden` の `span` を `li` の中に置く」。理由は、読み上げから外していることがコードで分かるため。欠点は、飾りの要素が HTML に増えること
4. **`nav` の名前。** 推奨は「現在位置」。理由は、デジタル庁デザインシステムに合わせ、役割をそのまま表すため。欠点は、「パンくずリスト」という呼び名に慣れた人には、すぐにはそれと分からないかもしれないこと
5. **どのページに出すか。** 推奨は「記事一覧・記事・タグ一覧・タグ別。ホームには出さない」。理由は、ホームに出しても「ホーム」1つだけになるため。欠点は、全ページで同じ位置に同じ部品がある一貫性が崩れること
6. **`main` の中に置くか。** 推奨は「`main` の中、見出しの前」。理由は、ページから中身を渡すので `main` の中にしか置けないため。欠点は、本文へスキップしたあと、Tab で最初に止まるのがパンくずになること
7. **記事ページの外枠。** 推奨は「`article` の外に `div` を作る」。理由は、パンくずは記事の中身ではないため。欠点は、入れ子が1段増えること
8. **構造化データを作るか。** 推奨は「この回では作らない」。理由は、この回を見た目と a11y に絞るため。欠点は、それまで検索結果にパンくずが出る機会を逃すこと
9. **展示室に出すか。** 推奨は「出さない」。理由は、展示室はページごとに自由にすると決めているため。欠点は、展示室から戻る道がヘッダーだけになること
10. **リンクに待ちの点を付けるか。** 推奨は「今は `next/link` のまま。`AppLink` ができたら差し替える」。理由は、起票した時点で `AppLink` が作りかけで、コミットされた形が決まっていなかったため。欠点は、差し替えるまでパンくずのリンクだけ待ちの点が出ないこと

## 確かめた結果

リポジトリの複製で確かめた（2026-11-19、bun 1.4.4 / Next.js 16.4.6 / markuplint 5.4.0）。

- `bun run tc`、markuplint、`bun run b` が通った
- ビルドした HTML で、`nav aria-label="現在位置"`、`ol` と `li`、`aria-hidden` の区切り、`aria-current="page"` の `span` が出ることを見た
- `bun run a11y`（axe、WCAG 2.2 AA）が light と dark の両方で通った
- 区切りの `span` を `ol` の直下に置くと、markuplint が `html-standard/permitted-contents` で止めた

VoiceOver での読み上げの文言は未確認。学習者が確かめたあとに書き足す。

## 影響

- 記事一覧・記事・タグ一覧・タグ別のページで、見出しの上にパンくずが1行増える
- 記事ページの外枠が `article` から `div` に移る。`article` の中身は変わらない
- 3-3 で付箋ページを作るときは、各ページに `Breadcrumb` を1つ書き足す
- 3-1b の `AppLink` がコミットされたら、`Breadcrumb` の `Link` を `AppLink` に置き換える
