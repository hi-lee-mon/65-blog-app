# 付箋の原稿を content/notes に置き、記事の読み込み処理を使い回して /notes に弁当レイアウトで並べる

- 日付: 2026-11-20
- 状態: 採用
- 関連: ADR `20261115-2117-publishable-home-before-storybook.md`（3-3 の位置づけ、`/notes` の推奨、`grid-lanes` の検討）、ADR `20260925-1914-unified-content-pipeline.md`（原稿の読み込みを Next.js に依存させない）、ADR `20260925-1907-content-in-same-repo.md`（Zenn 用の生成）、ADR `20261119-2126-breadcrumb.md`（パンくず）、ADR `20261115-2130-site-header-footer.md`（ヘッダーの `navItems`）、ADR `20261115-2200-page-a11y-check-with-axe.md`（axe の検査）

## 背景

記事より軽い「記事の種」を書いて公開する場所がほしい。書きかけのメモを付箋のカードにし、弁当レイアウトで並べるページを考えている（ADR `20261115-2117`）。メモは、書きかけのまま公開して育てる「デジタルガーデン」の考え方では「芽」にあたる。

ADR `20261115-2117` では、次の2点を 3-3 で決めることにしていた。

- 付箋ページの名前と URL。「Post-it」は 3M の登録商標なので、推奨は画面の名前を「付箋」、URL を `/notes` にする案
- 高さの違うカードを隙間なく詰める並べ方（masonry）。CSS の `grid-lanes` で書けるが、2026-11 時点で安定版が対応しているのは Safari 26.4 以降だけ。普通の CSS Grid で組み、対応するブラウザでだけ詰める形を検討する

原稿の読み込みを Next.js に依存させない制約（ADR `20260925-1914`）は、付箋の原稿にも当てる。

下書きのメモはすでに `content/draft/` に置いている。記事の読み込み処理 `createPostReader` は、渡したディレクトリの直下にある `.mdx` しか読まない。そのため `content/draft/` の中身は記事一覧に混ざっていない。

## 決めたこと

1. 画面の名前を「付箋」、URL を `/notes` にする
2. 原稿は `content/notes/*.mdx` に置く
3. 読み込みには `createPostReader` に `content/notes` を渡して使い回し、名前は変えない
4. frontmatter は記事と同じ形（`title`・`date`・`tags` を1〜5個）にする
5. 付箋ごとのページは作らず、本文をすべてカードに出す
6. 付箋の本文には見出しを使わない決まりにする。カードの題が `h2` なので、本文に `##` を書くと題と同じ階層になってしまう
7. 並べ方は普通の CSS Grid（`repeat(auto-fill, minmax(min(100%, {sizes.256}), 1fr))`、ブレークポイントなし）で組む。最低幅の 16rem は `sizes.256` のトークンにする（ADR `20261120-0914-escape-hatch-rule.md`）。`@supports (display: grid-lanes)` が通るブラウザでだけ `display: grid-lanes` で高さを詰める
8. `grid-auto-flow: dense` や `order` で見た目の順を入れ替えない。HTML の順（新しい順）と、読み上げや Tab で進む順をそろえる（WCAG 1.3.2・2.4.3）
9. 付箋の色は、この回では付けず、枠線だけにする
10. 幅は記事と同じ 640 にする。並ぶのは2列まで
11. 付箋のタグは、この回では画面に出さない

あわせて、次の3つを足す。

- `/notes` にパンくず（ホーム > 付箋）を置く
- ヘッダーの `navItems` に「付箋」（`/notes`）を足す
- axe の検査の入口（`e2e/a11y.spec.ts` の `ENTRY_PATHS`）に `/notes` を足す

カードは `NoteCard`（`app/_components/note-card.tsx`）にする。中身は `article` の中に題の `h2`、日付の `time`、本文を置いた形で、`ul` と `li` で並べる。

## 採らなかった案

- **付箋用の読み込み処理を別に作る。** 付箋だけの frontmatter（成熟度など）を持てる。ただ今は記事と同じ形で足りるので、同じ処理が2つになるだけになる
- **読み込み処理を `createContentReader` などの名前に変える。** 付箋も読むことが名前から分かる。しかし記事側の呼び出しも書き換えることになり、この回の範囲を超える
- **原稿をリポジトリ直下の `notes/` に置く。** Zenn 用の生成で `content/` を読むときに除く手間がない。そのかわり、原稿の置き場所が2か所に分かれる
- **付箋ごとのページを作る。** 1枚だけを共有できる URL ができる。ただし短いメモにページを作ると、ほとんど中身のないページが増える
- **CSS の `columns`（段組み）で並べる。** どのブラウザでも高さを詰められる。しかし上から下へ列ごとに流れるので、新しい順が横に読めなくなる
- **JavaScript の masonry ライブラリで詰める。** どのブラウザでも詰められるが、依存が増える。カードの位置を JavaScript で決めるので、表示されるまで位置が定まらない
- **`grid-auto-flow: dense` で隙間を埋める。** 見た目は詰まる。かわりに見た目の順と HTML の順がずれ、読み上げや Tab で進む順が、目で見た順と食い違う
- **付箋らしい黄色を付ける。** 見た目が付箋に近づく。ただ、色は必要になった回で、色覚と WCAG 1.4.1 を確かめてから足す方針にしている

## 確認事項の推奨と理由・欠点

チケットの「確認事項」と同じ内容。

1. **画面の名前と URL。** 推奨は「付箋」と `/notes`。理由は ADR `20261115-2117` で推奨した形であり、「Post-it」は登録商標のため。欠点は、英語の notes は「メモ」一般を指すので、付箋らしさが URL からは伝わらないこと
2. **原稿の置き場所。** 推奨は `content/notes/`。理由は、記事と同じ場所の下に置けば原稿が1か所にまとまり、記事の読み込み処理は直下しか読まないので混ざらないため（`content/draft/` と同じ仕組み）。欠点は、Zenn 用の生成で `content/` を読むとき、notes を除く処理が要ること
3. **読み込み処理。** 推奨は `createPostReader` をそのまま使い回し、名前は変えない。理由は、ディレクトリを渡せば付箋も読め、Next.js に依存しない制約もそのまま保てるため。欠点は、名前が「Post」なのに付箋も読むので、読んだ人が戸惑うこと。付箋の frontmatter を記事と変えたくなったら、処理を分ける必要がある
4. **frontmatter。** 推奨は記事と同じ形（`title`・`date`・`tags` を1〜5個）。理由は、3-4 の並べ替えに `date` と `tags` が要るため。欠点は、短いメモにも題とタグを毎回書く手間がかかること
5. **付箋ごとのページを作るか。** 推奨は「作らない」。理由は、短いメモは本文をカードに出せば読み切れるため。欠点は、1枚だけを共有する URL がないこと
6. **付箋の本文に見出しを使うか。** 推奨は「使わない決まりにする」。理由は、カードの題が `h2` なので、本文の `##` が題と同じ階層になってしまうため。欠点は、決まりを破っても検査では止まらないこと
7. **並べ方。** 推奨は「CSS Grid（`auto-fill`）で組み、`grid-lanes` は対応するブラウザだけ」。理由はどのブラウザでも崩れずに並び、対応するブラウザではそのまま詰まるため。欠点は、Chrome・Firefox（安定版）では行ごとに高さがそろい、短いカードの下に隙間が空くこと
8. **見た目の順を入れ替えるか。** 推奨は「入れ替えない」。理由は HTML の順（新しい順）と読み上げや Tab で進む順をそろえるため（WCAG 1.3.2・2.4.3）。欠点は、隙間を埋める詰め方ができないこと
9. **付箋の色。** 推奨は「この回では付けず、枠線だけ」。理由は、色は必要になった回で、色覚と WCAG 1.4.1 を確かめてから足す方針のため。欠点は、見た目が付箋らしくないこと
10. **幅。** 推奨は記事と同じ 640。理由は、各ページの幅をそろえるのは 3-7 で行うため。欠点は2列までしか並ばず、弁当らしい3列以上の並びは見られないこと
11. **付箋のタグを出すか。** 推奨は「この回では出さない」。理由は、タグの扱いは並べ替えと一緒に 3-4 で決めるため。欠点は、この回ではタグを書いても画面に出ないこと

## 確かめた結果

リポジトリの複製で確かめた（2026-11-20、bun 1.4.4 / Next.js 16.4.6 / @pandacss/dev 2.5.0）。

- `createPostReader("content/notes")` で付箋3件を読めた。`createPostReader("content")` で読む記事の数（11件）は変わらなかった
- Panda CSS の `css()` に `"@supports (display: grid-lanes)": { display: "grid-lanes" }` と書くと、型検査が通った。生成された CSS に `@supports (display: grid-lanes) { ... display: grid-lanes; }` が出た
- 付箋の frontmatter から `tags` を消すと、読み込みが「voiceover-basics.mdx の frontmatter が正しくありません × Invalid key: Expected "tags" but received undefined」で止まった。記事と同じ検証が付箋にも掛かる
- 整形の確認・lint・`bun run b` が通り、`/notes` が静的なページとしてビルドされた
- `/notes` を入口に足した axe の検査（`bun run ay`、WCAG 2.2 AA）が、light と dark の両方で通った
- ビルドした HTML で、`ul` > `li` > `article` > `h2`・`time`・本文の順に並ぶことを見た

Safari 26.4 以降で実際に高さが詰まるか、VoiceOver での読み上げの文言は未確認。学習者が確かめたあとに書き足す。

## 影響

- ヘッダーのナビに「付箋」が増える
- `content/notes/` に原稿を置けば、`/notes` に付箋が並ぶ
- axe の検査が `/notes` も見るようになる

## 今後

- 3-3b で、付箋の高さを制限し、選ぶと全文がダイアログで開くようにする。grid-lanes に対応していないブラウザで、行の高さが一番長い付箋にそろって見づらくなるため。開く動きは React の `<ViewTransition>` で付ける
- 3-4 で、付箋を日付とタグで並べ替え、タグを画面に出す
- Zenn 用の生成を作る回で、`content/notes/` を生成の対象から除く
- 付箋に色を足すときは、色覚の違いと WCAG 1.4.1（色だけで意味を伝えない）を確かめる
- 3-7 で、各ページの幅をそろえる。付箋ページの列の数もそこで見直す
