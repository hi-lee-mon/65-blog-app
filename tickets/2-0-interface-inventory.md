## なぜこれをやるか

いきなり色や部品を作り始めると、使わない部品が増えるうえに、今あるものとの食い違いにも気づけない。Brad Frost は『Atomic Design』第4章で、デザインシステムづくりの最初の一歩に interface inventory（今ある画面の部品を1種類ずつ集めて並べる棚卸し）を挙げている。

棚卸しで分かることは2つある。今のサイトに何があって何が足りないかと、見た目の値（色や文字の大きさ）がどこに書かれているかだ。この回の表が 2-2 で作るトークンの一覧と、2-5・2-6 で作る部品の一覧の元になる。ここを飛ばすと、2-2 で「どの色に名前を付ければよいか」を決める材料がない。

## 周辺知識

### デザインシステムの定義（出典: NN/g「Design Systems 101」、Therese Fessenden、2021-04-11）

「再利用できる部品とパターンを使って、大規模なデザインを管理するための標準一式」と定義している。中身として挙げているのは次の3つ。

| 中身           | 英語              | このブログでの例                             |
| -------------- | ----------------- | -------------------------------------------- |
| スタイルガイド | style guide       | 色・文字・余白の値（トークン）と、その使い方 |
| 部品の一覧     | component library | タグ、カード、メニュー                       |
| パターンの一覧 | pattern library   | 記事ページの組み方のような、部品の組み合わせ |

### トークンの3段（出典: Contentful「Design tokens」）

| 段             | 例                                 | 役割                                         |
| -------------- | ---------------------------------- | -------------------------------------------- |
| 基本 primitive | `blue.500` = `#3b82f6`             | 実際の値に名前を付ける                       |
| 意味 semantic  | 「本文の文字色」= `gray.900`       | 用途の名前。ダークモードではここを差し替える |
| 部品 component | 「タグの背景色」= 「控えめな背景」 | 部品ごとの名前。なくてもよい                 |

設計書の「① 基本トークン → ② 意味トークン → ③ ページテーマ」は、このうち上の2段に、ページごとの上書きを足したものにあたる。

### デジタル庁デザインシステムの構成（https://design.digital.go.jp/ 、2026-11-06 確認）

- 上の段: はじめに / ガイダンス / 基本デザイン / コンポーネント / リソース / お知らせ
- 基本デザインの8項目: カラー、タイポグラフィ、アイコン、レイアウト、リンクテキスト、余白、角の形状、エレベーション（影で表す高さ）
- コンポーネントの例: ボタン、パンくずリスト、チェックボックス、区切り線、ドロワー、ハンバーガーメニューボタン
- Figma のデータと、HTML 版・React 版のコードスニペットを配っている。デザイントークンは GitHub と Storybook で公開している

### Tailwind CSS の Preflight（出典: https://tailwindcss.com/docs/preflight ）

Tailwind CSS が最初に読み込むリセット用の CSS。modern-normalize をもとに、見出しの大きさと太さ、リストの記号、要素の外側の余白などを消す。リンクの色と下線は、親の要素から受け継ぐ。

### 準備：この回で何をするのか

今のサイトにある部品と見た目の値を、全部書き出す。書き出したものを4つの種類に分けると、デザインシステムで何から作ればよいかが見えてくる。この回ではアプリのコードを書かない。書くのは表だけだ。

#### デザインシステムは「レゴの規格」

レゴのブロックは何年に買ったものでも組み合わせられる。ポッチの間隔が決まっていて、色も決まった種類しかないからだ。この規格があるので、別々に作った部品どうしがぴったり合う。

デザインシステムも同じように、3つの層でできている。

| 層             | レゴでいうと                 | このブログでの例                      |
| -------------- | ---------------------------- | ------------------------------------- |
| トークン（値） | ポッチの間隔、使える色の種類 | 「本文の文字色」「余白の1段目は 8px」 |
| 部品           | 規格どおりに作ったブロック   | タグ、カード、メニュー                |
| 使い方の決まり | 組み立て説明書               | 「記事の見出しの上は余白3段」         |

規格がないと、部品ごとに「だいたいこのくらいの青」「だいたいこのくらいの余白」が生まれ、並べたときにずれる。デザインシステムはこのずれをなくす仕組みで、最初に作るのは規格、つまりトークンになる。

#### 棚卸しは「引っ越し前の持ち物リスト」

引っ越しの前に家にあるものを全部書き出すと、同じものが3つあったり、要るものがなかったりすることに気づく。interface inventory もこれと同じで、画面の部品を1種類につき1つずつ書き出す。同じリンクが10か所にあっても、書くのは1行でよい。

#### 用意するもの

- 1-13 までをコミットした `dev`
- Chrome（DevTools を使う）

### 手順 3：見出し・本文・リンクの見た目を、数字にして比べる

http://localhost:3000/posts/blog を開き、DevTools の Console タブに次のコードを貼って Enter を押す。

Chrome は初めてコンソールに貼り付けたときに警告を出して止める。警告の指示どおりに `allow pasting`（日本語表示では「貼り付けを許可」）と打ってから、もう一度貼る。

```js
const pick = (selector) => {
  const el = document.querySelector(selector);
  if (el === null) return { selector, fontFamily: "（この要素はない）" };
  const s = getComputedStyle(el);
  return {
    selector,
    fontFamily: s.fontFamily,
    fontSize: s.fontSize,
    fontWeight: s.fontWeight,
    color: s.color,
    underline: s.textDecorationLine,
    marginBottom: s.marginBottom,
  };
};
console.table(["html", "body", "h1", "h2", "p", "a", "pre"].map(pick));
```

`getComputedStyle` は、ブラウザが CSS をすべて当てはめたあとの「最終的な見た目の値」を返す関数だ。DevTools の Elements タブで要素を選び、Computed（計算済み）を開いたときに出る値と同じものが、表になって出てくる。`a` はページで最初のリンク、つまり上にある「ホーム」のリンクを指す。

| html     | Geist, "Geist Fallback"             | 16px     | 400        | rgb(0, 0, 0)    | none      | 0px          |
| body     | Arial, Helvetica, sans-serif        | 16px     | 400        | rgb(23, 23, 23) | none      | 0px          |

### 手順 4：見た目の値がどこに書かれているかを探す


`grep` に出てこない置き場所もある。シェア用の画像の背景は `background: "white"` と色の名前で書いてあり、16進数ではないので引っかからない。手順 3 で見た 404 ページの色は Next.js の中にある。

**なぜ** — 値の置き場所が1か所なら、そこを直せばサイト全体が変わる。何か所もあれば、直し忘れが起きる。次の手順で、それを実際に起こしてみる。

### 手順 5：わざと文字の色を変え、色が変わらない場所を見つける

`app/globals.css` の5行目と19行目にある `--foreground` を、両方とも赤（`#d00000`）に変える。5行目がライトモード、19行目がダークモードの文字色だ。

変える前:

```css
--foreground: #171717;
```

```css
--foreground: #ededed;
```

変えたあと:

```css
--foreground: #d00000;
```

```css
--foreground: #d00000;
```

保存すると、開発サーバーが自動で読み直す。http://localhost:3000/posts/blog を開き直し、手順 3 のコードに `time` を足した次のコードを貼る。

```js
console.table(
  ["body", "h1", "h2", "p", "a", "time", "pre"].map((selector) => ({
    selector,
    color: getComputedStyle(document.querySelector(selector)).color,
  })),
);
```

期待される出力:

| selector | color           |
| -------- | --------------- |
| body     | rgb(208, 0, 0)  |
| h1       | rgb(208, 0, 0)  |
| h2       | rgb(208, 0, 0)  |
| p        | rgb(208, 0, 0)  |
| a        | rgb(208, 0, 0)  |
| time     | rgb(208, 0, 0)  |
| pre      | rgb(36, 41, 46) |

目でも確かめる。

- 赤くなる: 本文、見出し、リンク、日付、目次
- 赤くならない: コードブロックの文字（Shiki のテーマが色を持っている）
- 赤くならない: http://localhost:3000/posts/nope の文字（Next.js が `#000` を指定している）
- 赤くならない: http://localhost:3000/posts/blog/opengraph-image の日付（`opengraph-image.tsx` に `#555` と直接書いてある）

確かめたら元に戻す。

```bash
git restore app/globals.css
git diff --stat app/globals.css
```

`git diff --stat` が何も出さなければ、元に戻っている。

**なぜ** — 色を1か所で変えたつもりでも、コードブロック、404 ページ、シェア用の画像は別の場所に色を持っているので、ついてこない。ダークモードやテーマの切り替えを作ると、これが「ここだけ白いまま」という不具合になって表に出る。トークンは値を1か所に集めて名前を付け、どこからでもその名前で参照する仕組みだ。2-3 ではシェア用の画像やコードブロックも同じトークンを参照できるかを確かめることになる。

### 手順 6：デジタル庁デザインシステムの「基本デザイン」と見比べる

https://design.digital.go.jp/dads/foundations/ を開く。基本デザインには次の8項目が並んでいる。

カラー、タイポグラフィ、アイコン、レイアウト、リンクテキスト、余白、角の形状、エレベーション

1つずつ開き、冒頭の数段落だけ読む。全部を読み込まなくてよい。読みながら、「このサイトでは、この項目に当たるものが今どうなっているか」を一言ずつメモしておく。たとえば「リンクテキスト: 本文と区別できない（手順 3）」のように書く。

**なぜ** — 自分のサイトだけを見ていると、「ない」ことに気づけない。たとえば、このサイトにはアイコンも角丸も影もまだない。本物のデザインシステムの目次と並べると、デザインシステムが何を決めておく道具なのかと、自分のサイトに何が足りないかが同時に見える。

### 手順 7：この回の本題。部品と値を4つの種類に分け、扱う回とつなげる

ここまでに集めたものを表にする。種類は次の4つ。

| 種類               | 何か                                                                 | 扱う回   |
| ------------------ | -------------------------------------------------------------------- | -------- |
| 値                 | 色、フォント、文字の大きさ、余白のように、数字や名前で表せるもの     | 2-2・2-3 |
| レイアウト         | 本文の幅、ページの上と下の骨組みのように、部品の並べ方               | 2-4      |
| 状態を持たない部品 | 見出し、リンク、タグ、目次、コードブロックのように、何も覚えない部品 | 2-4・2-5 |
| 状態を持つ部品     | メニューのように「今開いているか」を覚えていて、操作で変わる部品     | 2-6      |

「状態を持つ」は壁の絵と電気のスイッチの違いで考えるとよい。壁の絵は何度見ても同じだ。スイッチは「今オンかオフか」を覚えていて、押すたびに変わる。タグのリンクは押すと別のページに移るが、リンク自体は何も覚えていないので、絵の側に入る。ホバーやフォーカスで見た目が変わるのは CSS だけで書けるので、ここでは状態に数えない。

#### 7-a：表の枠を作る

`docs/design/inventory/README.md` を作り、次の内容を貼る。日付とコミットは自分の値に書き換える。コミットは `git log --oneline -1` の先頭7文字。

```markdown
# 見た目を作る前の棚卸し

- 棚卸しした日: 2026-11-xx
- コミット: xxxxxxx
- 分け方: 値 / レイアウト / 状態を持たない部品 / 状態を持つ部品（`tickets/2-0-interface-inventory.md` の手順 7）

## 部品と値

| 名前 | 種類 | どこにあるか | 今の見た目 | 気づいたこと | 扱う回 |
| ---- | ---- | ------------ | ---------- | ------------ | ------ |

## デジタル庁デザインシステムの基本デザインと比べて

| 項目 | このサイトでは |
| ---- | -------------- |

## スクリーンショット

![ホーム](home.png)
![記事一覧](posts.png)
![記事](post.png)
![表を書いた記事](post-table.png)
![タグ一覧](tags.png)
![タグ別の記事一覧](tag.png)
![404](not-found.png)
![シェア用の画像（サイト）](og-site.png)
![シェア用の画像（記事）](og-post.png)
```

#### 7-b：自分で表を埋める

手順 2〜6 で見たものを、「部品と値」の表に1行ずつ書く。スクリーンショットを1枚ずつ開き、目に入った部品を上から順に拾っていくと漏れにくい。「扱う回」の列は上の4種類の表から選ぶ。どの回にも当てはまらないものは「未定」と書いてよい。

「デジタル庁デザインシステムの基本デザインと比べて」の表には、手順 6 のメモを写す。

#### 7-c：答え合わせ

自分で埋め終わってから、次の例と見比べる。行の数や名前は違っていてよい。見落としていた行があれば足す。

| 名前                 | 種類               | どこにあるか                        | 今の見た目                                                    | 気づいたこと                                                                  | 扱う回             |
| -------------------- | ------------------ | ----------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------ |
| 文字の色・背景の色   | 値                 | `app/globals.css`                   | 文字 `#171717`・背景 `#ffffff`（ダーク `#ededed`・`#0a0a0a`） | コードブロック、404、シェア用の画像は別の色を持つ（手順 5）                   | 2-2・2-3           |
| フォント             | 値                 | `app/globals.css`・`app/layout.tsx` | 本文 Arial、コード Geist Mono                                 | Geist を読み込んでいるのに本文で使っていない。日本語のフォントは決めていない  | 2-2                |
| 文字の大きさ         | 値                 | どこにも書いていない                | すべて 16px                                                   | 見出しと本文の区別がない                                                      | 2-2・2-4           |

| 本文の幅             | レイアウト         | どこにも書いていない                | 画面いっぱい                                                  | 広い画面だと1行が長すぎて読みにくい                                           | 2-4                |

| 表                   | 状態を持たない部品 | `/posts/lib-or-util`・`/posts/dns`  | `\|` の文字のまま段落に入っている                             | 表の記法（GFM）を読むプラグインがない。見た目より前に原稿の読み込みの問題     | 2-4 で扱いを決める |

| ファビコン           | 値                 | なし                                | `/favicon.ico` が 404                                         | デジタル庁の「アイコン」に当たるものが何もない                                | 未定               |
| 状態を持つ部品       | 状態を持つ部品     | なし                                |                                                               | 今は1つもない。候補はテーマ切り替え、スマホ用のメニュー、コードのコピーボタン | 2-6                |

**表から分かること** — 表を種類ごとに数えると、3つのことが分かる。

- 一番多いのは「値」の行と、その値が決まっていないせいで区別がつかない部品の行。だから 2-2 でトークンから作る。値を決めないまま部品を作ると、部品ごとに色や余白を決めることになり、手順 5 で見た「ついてこない場所」が増えていく
- 状態を持つ部品は、今は1つもない。React Aria が役に立つのはこの種類の部品だけなので、出番は 2-6 まで来ない
- 部品の多くは記事ページにある。だから記事ページを最初の実戦の場（2-4）にする。Dan Mall が勧める「実際のページで使いながら育てる」進め方にあたる

この3つが、この段の順番の理由そのものになっている。2-1 以降で「なぜ今これを作るのか」と迷ったら、この表に戻ってくればよい。

## 受け入れ条件

- [ ] `ls docs/design/inventory/*.png | wc -l` が `9` を出す
- [ ] `file docs/design/inventory/og-site.png docs/design/inventory/og-post.png` が、2つとも `PNG image data, 1200 x 630` を含む
- [ ] `docs/design/inventory/README.md` の「部品と値」の表に、4つの種類それぞれの行が1行以上ある（状態を持つ部品は「なし」の行でよい）
- [ ] 「部品と値」の表の「扱う回」の列が、全行埋まっている（「未定」でもよい）
- [ ] 「デジタル庁デザインシステムの基本デザインと比べて」の表に、8項目すべての行がある
- [ ] `git diff --stat app/globals.css` が何も出さない
- [ ] `dev` にコミットされ、push されている（`git status` が `Your branch is up to date with 'origin/dev'.` を出す）

## この回で理解したこと

着手後に埋める。受け入れ条件とは別に、何が分かったかを残す。

- [ ] デザインシステムが「値（トークン）」「部品」「使い方の決まり」の3つでできていることを、レゴのたとえを使わずに説明できる
- [ ] 今のサイトで、見出しと本文が同じ見た目になっている理由を説明できる
- [ ] 手順 5 で色が変わらなかった場所を3つ挙げ、それぞれなぜ変わらなかったかを説明できる
- [ ] 状態を持つ部品と持たない部品の違いを、このサイトの例（または、これから作る部品の例）で1つずつ挙げられる
- [ ] React Aria を 2-6 まで使わない理由を、棚卸しの表を根拠に説明できる
